# Step 02 — Feature lists (cross-batch alignment)

Turns raw LC-MS/MS runs into one feature table per ionisation mode
(Supplementary Method 1). Samples were measured in **6 independent batches**;
each batch was first processed on GNPS as an FBMN job, then this step aligns
the six batches into one table so the same molecule gets the same `feature_id`
everywhere.

## What happens inside

Both modes: raw mzML → **MZmine 4.9** feature detection per batch (IIMN
workflow) → **GNPS2 FBMN** per batch → RT drift correction → cross-batch
consensus. The two modes used **different implementations** (both recovered,
both verified against their outputs):

**Positive mode** (`alignment_pipeline_POS.py`, reference-centric):

| Sub-step | What it does |
|---|---|
| 1. Anchor discovery | Features present in ≥3 of 6 batches (5 ppm, ±2 min) — >15,000 anchors |
| 2. RT drift | Drift of each batch vs reference batch OE23-POS |
| 3. LOESS correction | Single-pass LOESS smooths the drift (residual 0.35–0.52 min) |
| 4. Consensus | Every batch matched **to the reference** (5 ppm, ±0.5 min); RT window 1.5–25 min |
| 5. Library integration | GNPS matches + families merged → combined TSVs |

**Negative mode** (`neg/rt_correction_v2.py` + `neg/align_consensus.py`, cascade):

| Sub-step | What it does |
|---|---|
| 1. RT correction v2 | **Iterative LOWESS** (10 rounds, tightening tolerance, MAD outlier rejection) per batch vs OE23-NEG |
| 2. Cascade consensus | Consensus seeded from OE23-NEG, then each batch (largest→smallest) matched **to the growing consensus**; biological samples only; RT window 1.5–21 min |

**Result:** 273,248 features × 263 samples (positive); 122,571 × 200 (negative).
The NEG producer is verified by its own saved run receipt
(`neg/alignment_stats.csv`: cascade ends at exactly 122,571) and by a
byte-identical output archive (matching SHA-256) recovered from the original
analysis workstation.

> ⚠ **Known discrepancy with the manuscript Methods text.** Supplementary
> Method 1 describes negative mode as "processed equivalently" to positive
> mode. As documented above, the recovered and verified NEG implementation in
> fact used an improved iterative-LOWESS RT correction and a cascade (not
> reference-centric) consensus. Likewise, the phrase "mapped to the classical
> networking backbone" does not describe the verified POS code, which aligns
> each batch directly to the reference batch with no networking backbone.
> This repository documents the implementations as they actually ran.

Reads: ← 6 FBMN batch results from GNPS (quantification, library matches,
cluster summaries per batch) + sample metadata.
Used by: → 03 biomarker atlas and everything after it.

## Provenance notes and declared limitations

- ✅ **All 12 FBMN batch exports (6 POS + 6 NEG) are archived** in the analysis
  archive (see `data_registry/registry.csv`), so the whole alignment can be
  rerun offline. Raw mzML files are on MassIVE.
- Intermediates (anchor lists, LOESS curves, per-batch `*_rt_corrected.csv`)
  were not archived in either mode; they are regenerated by rerunning the
  scripts on the FBMN exports.
- **POS MZmine batch files: 1 of 6 recovered.** The OE23-POS batch ran on the
  University of Vienna Life Science Compute (LISC) cluster; its batch file,
  wizard presets, and SLURM runner are in `mzmine_pos_oe23/` (run log and full
  evidence in the analysis archive). The parameter files of the other five POS
  batches were not located on any archived system. If ever needed, the full
  MZmine batch template embedded in `generate_neg_mzmine_jobs.py` (analysis
  archive) provides a rebuild route.
- **MZmine version.** The recovered OE23-POS batch ran MZmine **4.9.0**; the
  Methods text states 4.9.14 for all batches. The recovered evidence supports
  4.9.0 for that batch; the version for the other five POS batches is not
  independently verifiable from archived parameter files.
- POS GNPS2 submission/download automation is preserved in `pos_gnps2/`
  (submission driver, downloader, task-state record).
